# CLAUDE.md

## Project Overview

WeatherEdge is a weather-driven trading bot for Polymarket daily "highest temperature in [city]" markets. Two trading paths run concurrently:

1. **Probability path** — every 5 minutes, aggregate live METAR observations + a deterministic Open-Meteo forecast (with multi-model ensemble σ) per city, build a probability distribution over integer temperature buckets, compare to live Polymarket CLOB prices, and size positions via fractional Kelly.
2. **Lock-rule path** — every 30 seconds, re-check active binary markets for new routine METARs and fire deterministic trades when the daily max is mathematically locked above (or below) threshold.

Resolution source is the Wunderground history page, which mirrors **routine** (non-SPECI) METARs. The bot reads METARs directly and typically sees the same data 1–2 hours before the UI updates — that's the edge both paths exploit.

> **Decision marks:** `docs/graveyard.md` is the single index of every **removed** and **suspended** (gated-off) hypothesis — what it was, why it's gone/off, and the re-enable criterion. Each suspended flag in `src/config.py` carries a one-line `# GRAVEYARD:` sentinel pointing to its anchor. Before re-enabling any default-off flag or re-attempting a killed idea, read its graveyard entry.

## Architecture

### Pipeline (critical path)

The unified pipeline runs in `src/scheduler/__init__.py::job_unified_pipeline` every 5 min. `job_fast_lock_poll` runs every 30 s.

```
circuit_breakers ─► get_active_weather_markets ─► group by ICAO (skip _EXCLUDED_ICAOS)
        │                                             │
        ▼                                             ▼
  Phase 1 (concurrent, sem=8):                 Phase 2 (sequential, per market):
    aggregate_state(session, icao, lat, lon)     ├─ skip future-day markets
      ├─ fetch_metar_history(icao, 24h)          ├─ get_token_ids (Gamma)
      ├─ fetch_deterministic_forecast \\         ├─ get_best_bid_ask → live yes_price
      │  +  fetch_ensemble_forecast    } gather  ├─ get_orderbook_depth
      ├─ _blend_forecasts (det. central +        ├─ _try_lock_rule_trade — if locked: size,
      │   ensemble σ at peak hour)               │   filter, place_order, continue
      ├─ get_bias(session, icao)                 ├─ skip if price ≥ 0.99 or ≤ 0.01
      ├─ check_and_record_daily_max_alert        ├─ compute_distribution(state, buckets)
      └─ returns WeatherState                    ├─ _binary_market_edge
                                                 ├─ size_position (fractional Kelly × dd_mult)
                                                 └─ place_order

  job_fast_lock_poll (30s):
    fetch_latest_metars(active_icaos) ─► for each new routine (icao, market):
        evaluate_lock(_minimal_state, market) ─► _try_lock_rule_trade
        _fast_poll_projection_check(icao, station_metars) — reuses _state_cache
```

`_locked_markets_fired_today`, `_last_routine_seen`, and the `_state_cache` (in `state_aggregator.py`) are in-process dicts cleared **per-station at the station's local-day rollover** by `_maybe_clear_per_station_caches` (called at the top of every `job_unified_pipeline` tick). A sibling `_market_to_icao` map populated at lock-fire time lets the rollover find which `market_id` entries belong to which station; `_local_day_seen` cookies the last-observed `today_local(tz)` per ICAO. A bias-runaway station (`|bias| > 3°C`) is skipped at Phase 1 grouping.

`job_fast_lock_poll` only fires the **EASY** lock direction (observed max already clears threshold + margin). The **HARD** direction (no-more-heating: market-day max below threshold AND past-peak signal AND forecast peak < threshold) needs full forecast context and stays in `job_unified_pipeline`. For the **forecast-exceedance projection** check, fast-poll reuses the previous unified tick's forecast / bias / climate-normals via `_state_cache` (30-min TTL keyed by ICAO).

## Key Patterns

### Probability engine (`src/signals/probability_engine.py`)

`compute_distribution(state, buckets)` produces a `BucketDistribution` with `probabilities: {bucket_f: prob}` summing to 1.0.

Signal combination:

1. **Baseline Gaussian** centered on `state.forecast_peak_f` (deterministic Open-Meteo peak + 30-day station bias).
1a. **Climate-prior blend (`_apply_climate_prior`)** — when `state.climate_prior_mean_f`/`_std_f` are populated, treats the baseline as the likelihood and the climatology as the prior, returning the precision-weighted Bayesian posterior (tightens σ, pulls center toward whichever input has lower variance; floored by `CLIMATE_PRIOR_MIN_SIGMA_F=2.0` to keep tropical/oceanic stations with σ ≈ 1°F from collapsing the posterior). **No-op today** — `CLIMATE_PRIOR_ENABLED=False` and `station_normals` is unpopulated pending the backfill loader (see `docs/improvements.md` [climate-prior backlog] + `src/ingestion/station_normals.py`).
2. **σ from `_compute_sigma`**: ensemble spread when available (`forecast_sigma_f × ENSEMBLE_SPREAD_MULTIPLIER=1.3`), clipped to `[combined_floor, ENSEMBLE_MAX_SIGMA_F=5.0]`°F. `combined_floor` composes three arms: (a) `_effective_sigma_floor(state)` — per-station rolling forecast-error RMSE (clamped to `[1.5, 5.0]`°F) when the station has ≥`_PER_STATION_SIGMA_MIN_DAYS=14` days of `station_biases` rows, else the global `ENSEMBLE_MIN_SIGMA_F=2.0` (per-station floor exists because a single global 2.0°F over-pads low-variance stations and under-pads high-variance ones); (b) **lead-time additive arm** — `SIGMA_LEAD_TIME_SLOPE_F_PER_HR × max(0, hours_until_peak)` gated by `SIGMA_FLOOR_LEAD_TIME_ENABLED` (default False = no-op); stops a confident ensemble from collapsing σ far from peak (the Amsterdam σ-collapse class — see `BRACKET_LIKE_NO_DISABLED` and `docs/improvements.md`); (c) soft hours-based floor scaled by `SIGMA_HOURS_FLOOR_MULTIPLIER` (default 0.5; raise to 1.0 in `.env` for moderate-lead bite). The reasoning trail surfaces `lead_floor=` + the multiplier so a tight-σ day shows which arm bound. All three arms are no-ops at `hours_until_peak ≤ 0` (past peak). Hours-based fallback (no-ensemble): 1.0 past peak, 1.5 (≤2h), 2.5 (≤4h), 3.5 (>4h).
3. **METAR trend shift** (three branches): *pre-peak* — shift by residual rate (`metar_trend_rate − forecast_slope_to_peak_f_per_hr`) when ≥0.5°F/hr, capped at +2°F (falls back to raw rate when forecast slope missing); *past peak + declining* (`rate ≤ 0`) — lock center to observed max; *past peak + still rising* (`rate > POST_PEAK_MIN_TREND_F_PER_HR=0.5`) — extrapolate `rate × hours × POST_PEAK_TREND_CARRY_K (0.75)`, capped at `POST_PEAK_MAX_SHIFT_F=3°F`, damped by solar/cloud magnitudes.
4. **Solar/cloud cap**: combined `solar_declining` AND `cloud_rising` → hard cap at observed max. Strong solar decline alone (`solar_decline_magnitude > 0.7`) → soft cap at `observed_max + 1°F`.
5. **Dewpoint adjustment**: rising Td >1°F/hr tightens sigma (max 0.5°F); falling Td <-1°F/hr widens it (max 0.3°F).
6. **Monotonicity constraint** (hard): `P(bucket < current_max_f) = 0`. Degenerate fallback collapses all mass to bucket closest to `current_max_f` when zeroed.

Every applied signal is appended to `distribution.reasoning`.

### State aggregator (`src/signals/state_aggregator.py`)

`aggregate_state` returns a `WeatherState` snapshot per city. Key fields:

- `metar_trend_rate` / `metar_trend_rate_short` — 6h and 2.5h linear regressions on routine METAR temps. Probability engine uses the 6h slope; `forecast_exceedance` uses the 2.5h slope.
- `routine_history` — sorted `(observed_at_utc, temp_f)` tuples for last 24 h. `lock_rules._market_daily_max` uses this to compute per-market daily max anchored to `market.end_date`'s **station-local** day.
- `latest_obs_temp_f`, `forecast_temp_now_f`, `forecast_slope_to_peak_f_per_hr`, `forecast_residual_f` — bias-adjusted residuals.
- `forecast_residual_slope_f_per_hr`, `forecast_residual_count` — `d(residual)/dt` linear regression over routines (computed by `_compute_residual_slope`). Drives v2 path of `_project_daily_max` when count ≥3.
- `forecast_sigma_f`, `ensemble_model_count` — ensemble σ at peak hour (None when ensemble unavailable).
- `has_forecast` — gates HARD-direction lock evaluation.

When Open-Meteo fails entirely, `WeatherState` is still returned: `forecast_peak_f = current_max_f`, `hours_until_peak = 0`, solar/cloud signals False, `forecast_sigma_f = None`, `has_forecast = False`. Probability distribution degenerates to a narrow band; lock rule's HARD direction is disabled. The METAR / deterministic / ensemble fetches now run with `asyncio.gather(..., return_exceptions=True)` — a 5xx from the ensemble endpoint no longer voids the deterministic-only fallback, and a deterministic failure no longer voids ensemble-alone (lossy bias frame but at least usable for distribution width).

After every successful aggregation, `aggregate_state` stashes its inputs (`forecast`, `bias_c`, `climate_prior_*`, `history`, timestamp) into the module-level `_state_cache` keyed by ICAO (30-min TTL). Fast-poll reads via `get_cached_aggregation_inputs(icao)`.

### Lock-rule trader (`src/signals/lock_rules.py` decision + `src/execution/lock_rule_executor.py` side effects)

Deterministic complement to the probability engine. Returns a `LockDecision(side, reasons, margin_f)`.

Operators in scope:
- **Threshold** (`above`, `at_least`, `below`, `at_most`) — EASY/HARD branches below.
- **Range / bracket / `exactly`** — routed through `_evaluate_range_lock`. `market_range_f` (in `execution/binary_market.py`) builds the `[low_f, high_f]` window: parsed `(low, high)` for explicit brackets, synthetic single-bucket range for `exactly` (e.g. `=10°C` → `[50, 51]°F`). Fires NO on **overshoot** (`bucket_overshoot`, see below), NO on undershoot (`current_max_f <= low_f - 2 × LOCK_MARGIN_F` AND `_no_more_heating`, `routine_count >= RANGE_LOCK_MIN_ROUTINES=4`), YES on in-range (past-peak with no upward signal).
- **`bucket_overshoot` (the one verified edge; `BUCKET_OVERSHOOT_LOCK_ENABLED`, default False).** Buy NO once the market-day running routine max has climbed `BUCKET_OVERSHOOT_MARGIN_C` (1) whole °C above the bucket top — the daily max is monotonic, so the bucket can never win. **Certainty, not forecast**: the only loss mode is resolver divergence, so (a) `BUCKET_OVERSHOOT_EXCLUDED_STATIONS` drops the four stations whose `P(divergence ≥ 1°C) > 5%` (ZGSZ 34.5%, MPTO 30.8%, EGLL 26.9%, UUEE 14.8%; every other station with n≥15 is ≤4.2%), and (b) the executor rejects any fill above `BUCKET_OVERSHOOT_MAX_COST=0.93`. The boundary is computed in the market's own unit by `_bucket_dead_threshold_f` (°C markets step 1.8°F, °F markets 1.0°F) — **not** from `market_range_f`'s rounded integer window, whose width is not a whole °C step. This supersedes the mistakenly-removed `range_overshoot` (see `docs/graveyard.md` — its "−$57.61" was phantom-inflated and its one real loss was the pre-05-26 wrong-day bug). **Speed is the edge**: the market reprices a median **2.1 min after the METAR observation time** and we receive it at a median **2.7 min**; EV survives a ~30 s decision delay and dies by ~60 s, so this branch must fire from `job_fast_lock_poll` (30 s), never the 5-min unified tick.

**Lowest/minimum temperature markets are filtered upstream** in `polymarket.parse_question` (`_LOWEST_TEMP_RE`) — the pipeline assumes daily-max physics. A defensive guard in `evaluate_lock` also drops them by question-text match.

Two threshold-market directions:

- **EASY** — market-day max ≥ threshold + `LOCK_MARGIN_F` (2.0°F). Mathematically locked. Decides YES for `above`/`at_least`, NO for `below`/`at_most`. No forecast required.
- **HARD** — market-day max < threshold − margin AND `_no_more_heating(state, threshold)` (requires `has_forecast`, `forecast_peak_f < threshold`, `hours_until_peak <= 0` pre-peak guard, AND past-peak signal: `solar_declining` OR `metar_trend_rate ≤ 0`). Decides NO for `above`/`at_least`, YES for `below`/`at_most`. The same `hours_until_peak <= 0` gate applies to `range_undershoot`. **Gated by `HARD_LOCK_ENABLED` (Settings, default `True`; the live env sets it `False`) since 2026-06-30** — the prod audit (workflow `wf_3496e753-f0b`) found HARD was the #1 active lock bleed (−$16.97/30d, −$7.63 excl. the now-`_EXCLUDED_ICAOS` Taipei/RCTP): all 10 fills ever are BUY_NO, tiny wins vs large losses, and **every loss carried a 14–20°F lock margin yet still lost** — a >14°F forecast miss that no margin/σ-floor tweak fixes (the lead-time σ floor only touches the probability engine). Read live off `settings`; re-enable only after the forecast-miss class is explained (resolver-station verification) and the branch turns +EV.

Per-market daily max comes from `_market_daily_max(state, market.end_date, now_utc)` — anchored to the market's **title day** = `resolve_target_local_day(end_date)` = `market.end_date`'s **UTC date** (= the question-text day; see the data-day gotcha below), source `state.routine_history`.

Routine-count gates:
- **Super-margin EASY** (overshoot ≥ 2× `LOCK_MARGIN_F`): allowed at routine_count = 2 (monotonicity makes two confirming obs already 4°F+ over threshold bulletproof).
- **Standard EASY / HARD**: require `MIN_ROUTINE_COUNT` (3).
- **Range overshoot/undershoot**: require `max(MIN_ROUTINE_COUNT, RANGE_LOCK_MIN_ROUTINES=4)` + 2× margin bound. The `range_in_window` (YES) branch is *not* tightened — its filter is already stricter (forecast caps + past peak + no upward signals).

`_try_lock_rule_trade` flow: (1) `evaluate_lock` → return None if no side; (2) `effective_price` = `yes_price` (YES) or `1 - yes_price` (NO), reject outside `[LOCK_RULE_MIN_PRICE=0.05, LOCK_RULE_MAX_PRICE=0.95]`; (3) `_check_filters` with `min_routine_count=2` (already gated), close buffer, depth — stub edge/prob, no edge gate; (4) size via `size_locked_position` (`LOCK_POSITION_PCT=2%`, capped at `MAX_POSITION_USD/2` and 15% of depth — **or** conviction Kelly-by-price for a whitelisted EASY-YES lock when `LOCK_CONVICTION_SIZING_ENABLED`; see Kelly sizing), apply drawdown multiplier, place FAK (conviction locks walk the book up to `LOCK_WALK_MAX_PRICE`); (5) write `Signal(model_prob=1.0, market_prob=effective_price, edge=1-effective_price)` and `Trade(direction, stake_usd, entry_price=effective_price)`. Telegram 🔒 alert.

Settings: `LOCK_RULE_ENABLED`, `LOCK_RULE_{MIN,MAX}_PRICE`, `LOCK_MARGIN_F`, `LOCK_POSITION_PCT`, `FAST_LOCK_POLL_{ENABLED,INTERVAL_SECONDS}`. Range constants are module-level in `lock_rules.py`: `RANGE_LOCK_MIN_ROUTINES=4`, `RANGE_LOCK_MARGIN_MULTIPLIER=2.0`. **`BUCKET_OVERSHOOT_LOCK_ENABLED` (default `False`) + `BUCKET_OVERSHOOT_MARGIN_C=1.0` + `BUCKET_OVERSHOOT_MAX_COST=0.93` + `BUCKET_OVERSHOOT_EXCLUDED_STATIONS="ZGSZ,MPTO,EGLL,UUEE"`** gate the `bucket_overshoot` NO branch — the project's **only edge validated against real executable prices** (3,580 rule-triggered candidates priced off CLOB 1-min history at the bot's true METAR arrival time, on-chain truth, event-clustered: 63 bets / 52 station-days, 2 losses, **EV +0.91/$1 [95% CI +0.53, +1.46]**; out-of-sample after 2026-06-05: 55 bets, 0 losses, +1.01/$1). On trusted stations the "dead" bucket wins 3/3580 = 0.08% of the time. Raising `MAX_COST` to 0.99 adds volume but makes >⅓ of bets −EV if divergence were 5× worse than observed. **`RANGE_UNDERSHOOT_LOCK_ENABLED` (Settings, default `True`; the live `.env` sets it `False`)** gates the `range_undershoot` NO branch — added 2026-06-03 after the audit showed it is **model-overconfident, not a resolver divergence**: it won 71.4% but its avg NO price 0.808 implies an 80.8% break-even (a NO bet's break-even win-rate = its price), so ~9pp overconfident → −$26.52 / 35 trades / 30d, the same win-small/lose-big shape as the killed bracket-like NO. Measurable resolver divergence is unbiased (±0.1°F), so a °C correction would not help; the cure is the deferred lead-time-aware σ floor (σ is too tight on narrow windows). **NOTE the default is `True`, so the gate only engages when the `.env` line is present** — re-enable (`True`) only after `SIGMA_FLOOR_LEAD_TIME_ENABLED` lands and the class turns +EV. `range_in_window` (YES) is unaffected by either flag (both read live off `settings`). **`HARD_LOCK_ENABLED` (Settings, default `True`; live env `False`)** gates the HARD branch in `evaluate_lock` (see HARD direction above). **`RANGE_IN_WINDOW_MIN_YES_PRICE` (Settings, default `0.80`)** gates the `range_in_window` YES branch in the executor (`lock_rule_executor.try_lock_rule_trade`, after the `LOCK_RULE` price check): a YES lock whose `effective_price < RANGE_IN_WINDOW_MIN_YES_PRICE` is rejected with reason `range_in_window price … < min …`. Added 2026-06-30 after the audit found the only realized `range_in_window` fill ever was a 0.40-priced "exactly" YES gamble that lost −$9.28; set `0.0` to disable the gate.

### Shadow decision flow (redesigned pipeline, 2026-06-12 — `src/signals/shadow_decision.py`)

A ground-up rethink of the decision pipeline, running in **shadow mode** (writes the
`shadow_ledger`, places **no orders**) alongside the untouched live probability + lock paths. Built
around ONE falsifiable edge thesis: **our edge is information latency, not better forecasting** — we
read routine METARs (the resolution source) before the market reprices, so our edge is the
conditional distribution of the daily max *given observations the market hasn't priced*, which is
maximal near/after peak and ~0 far from peak. The lock path is the degenerate certain case.

Four pure, independently-testable stages (replacing the ~38-veto wall, which was filtering used as a
substitute for a real edge estimate):
1. **`estimate_probability`** — a small inspectable model producing a *forecast prior* (≈ what the
   market knows: Gaussian on `forecast_peak_f` with a **lead-time-aware σ floor** — the long-deferred
   σ-collapse fix finally lives here) and an *observational update* (σ tightens with `obs_fraction` =
   fraction of the day's heating observed; mean shifts by today's damped forecast residual; hard
   monotonic floor at the **target-day-anchored** observed max), plus the **information-advantage**
   scalar (updated − prior). The floor's max is passed in as `estimate_probability(..., anchored_max_f=)`
   computed by `record_shadow_decision` via `lock_rules._market_daily_max(state, market.end_date, now_utc)`
   — NOT `state.current_max_f`, which is the station's rolling/aggregation-day max and leaks a
   neighbouring local day's peak into a pre-peak market (it spuriously locked YES→1.0; fixed 2026-06-16,
   exposed by the YES side the 2026-06-14 depth fix unblocked). Falls back to `state.current_max_f` only
   when the market's day hasn't started (helper returns None).
2. **net_edge** (via `cost_model`) — `prob − effective_cost`, friction first-class (fee + spread +
   size-vs-depth slippage), fixing the legacy `edge = prob − ask`.
3. **`decide_bet`/`_apply_gate`** — a SINGLE rule: trade iff `net_edge > k·σ_edge`, where `σ_edge`
   is wide far from peak (low `obs_fraction`) and tight near peak. Forecast disagreement alone can't
   clear the bar; only observation-backed edge can. Plus a hard liquidity/time floor.
4. **`size_bet`** — fractional Kelly on the cost-adjusted odds × observational-confidence shrinkage ×
   concentration cap. Size expresses edge AND uncertainty — no veto filters.

Wired via `shadow_ledger.record_shadow_decision` in `job_unified_pipeline` (best-effort, never
mutates the Market row). **Promotion gate:** `cli calibration-report` scores `shadow_ledger` vs the
market-price baseline (Brier + log-loss) bucketed by `obs_fraction`; route live capital to the new
model **per bucket** only once it beats the baseline OOS. Until then the new model touches no money.
Tunables live in `shadow_decision.ShadowParams` (not yet Settings — promote when going live).

### Edge calculator (`src/signals/edge_calculator.py`)

Filter checks delegate to `_check_filters()`. (The older multi-bucket `compute_edges` path was retired 2026-05-30 — see `docs/graveyard.md`.)

Rationale (2026-06-19): the realized June book split sharply by the **price of the side bought** — everything < ~0.80 lost (−$42 / 26 trades), the 0.80–1.00 near-lock band won 94% (+$17 / 18), and `calibration-report` showed the probability model does NOT beat market in any obs-fraction bucket (the edge is the price band, not the model). Setting `PROBABILITY_MIN_ENTRY_PRICE=0.80` concentrates the probability path on the near-lock band while the lock path keeps firing cheap-but-certain bets (where a low price is *good*).

**Probability-path forecast-required guard (threshold NO).** `binary_market_edge` takes `has_forecast: bool | None` (threaded from `state.has_forecast` at the `job_unified_pipeline` call site). When `PROBABILITY_THRESHOLD_NO_REQUIRE_FORECAST` (Settings, default `False`; **live env `True`**) is on, an `above`/`at_least` **BUY_NO** edge is rejected with reason `"threshold NO without forecast (degenerate state)"` when `has_forecast is False` — fired after the bracket-like guards under the `reason is None` guard, no-op when `has_forecast` is None/True. Rationale (2026-07-07 mastering audit, workflow `wf_beb30c80-6a3`): after the HARD-lock kill the remaining drag is the probability-path "forecast-cool NO" cohort — the **same bet** as the killed HARD-lock, still firing because the probability path lacked the `has_forecast` guard the HARD-lock path enforces. On an Open-Meteo failure the state degenerates (`has_forecast=False` → `forecast_peak_f == current_max_f`, σ NULL), the model prob collapses to ~1.0 and Kelly sizes the max — 3 of the 4 big post-06-30 losses (incl. Shanghai −$27.52) are these degenerate states. Same class as the conviction-gate degenerate-state bug (memory `project_conviction_degenerate_state_bug_2026-06-21`). Do **not** "require past-peak" — the data shows past-peak is the *losing* subset.

### Station bias (`src/ingestion/station_bias.py`)

Per-ICAO rolling mean of `observed_daily_max_c - forecast_peak_c` over `STATION_BIAS_WINDOW_DAYS` (30). Added to Open-Meteo peak to produce `forecast_peak_f`.

- `get_bias(session, icao)` — 30-day mean, falls back to `DEFAULT_STATION_BIAS_C` (1.0°C) when no history.
- `record_daily_outcome(...)` — called in `job_daily_settlement` for every station with ≥3 routine METARs.
- `is_bias_runaway(session, icao)` — returns True when `|bias| > STATION_BIAS_MAX_C` (3°C). Such cities are skipped in Phase 1 for that tick.
- `get_station_rmse(session, icao)` — 30-day rolling `sqrt(avg(bias_c²))` over the same window, converted to °F. Returns `(rmse_f, sample_days)`. In-process TTL cache (`_RMSE_TTL=1h`). Drives the per-station σ floor in `probability_engine._compute_sigma`; falls back to global `ENSEMBLE_MIN_SIGMA_F` when `sample_days < 14`. Computed on-the-fly from the existing `station_biases` rows — no new schema, no nightly job.

Bias is recorded against the deterministic single-source peak (not the ensemble blend) so the reference frame stays stable when the ensemble model list changes.

### Kelly sizing (`src/risk/kelly.py`)

`size_position()` applies cascading caps:
1. Fractional Kelly with `KELLY_FRACTION=0.25`
2. Per-trade cap: `MAX_POSITION_PCT=5%` of bankroll
3. Total exposure cap: `max(MAX_EXPOSURE_PCT=25% × bankroll, MAX_EXPOSURE_USD_FLOOR=$300)` minus current open exposure. The USD floor binds at small bankroll (< ~$1200) so a few stuck OPEN trades can't pin the cap and silence the bot
4. Hard USD cap: `MAX_POSITION_USD=200`
5. Orderbook depth cap: `DEPTH_POSITION_CAP_PCT=20%` of visible depth
6. Minimum viable trade: `MIN_TRADE_USD=5` (below returns 0, unless `floor_to_usd` is passed — see below)

Drawdown monitor multiplier (`DrawdownMonitor.check`) is applied on top of Kelly stake before the `MIN_STAKE_USD` check. The lock-rule path (`size_locked_position`) uses fixed sizing instead of Kelly: `LOCK_POSITION_PCT=2%`, capped at `MAX_POSITION_USD/2=$100` and 15% of depth — but `MAX_EXPOSURE_PCT`, `MIN_TRADE_USD`, and drawdown multiplier still apply.

**Conviction-weighted lock sizing (default-off).** `size_locked_position` takes optional `win_prob`/`kelly_fraction`/`max_position_pct`/`depth_cap_pct`. When `win_prob` is set it sizes by **fractional Kelly against the contract price** instead of the flat 2%: `b=(1−price)/price`, `f*=max(0, win_prob − (1−win_prob)/b)`, `frac=min(f*×kelly_fraction, max_position_pct)`. **No `KELLY_PROB_CAP`** (that cap tames the noisy probability path; a physically-locked, station-verified bet legitimately sits near 1.0); the same exposure / `MAX_POSITION_USD/2` / depth (`depth_cap_pct`) / `MIN_TRADE_USD` cascade + drawdown multiplier still apply. The executor (`lock_rule_executor.try_lock_rule_trade`) only opts a lock into this path when **all** of: `LOCK_CONVICTION_SIZING_ENABLED`, `decision.side == "YES"`, `decision.branch ∈ {easy_super, easy_standard}` (the truly monotonic, resolver-divergence-clean class), and `icao ∈ LOCK_BIG_SIZE_STATIONS` (whitelist). Otherwise it falls back to the flat 2% path (which still owns near-peak floor-up). Conviction locks also **walk the book**: `place_order` is passed a widened `max_slippage_cents` so the FAK sweeps every ask up to `LOCK_WALK_MAX_PRICE`. Rationale: the EASY-YES lock is the bot's one genuinely-near-certain edge but was sized like its weakest bets (~$9 at a $456 bankroll); Kelly-by-price turns a near-certainty at a discount into a real position (~$68 at the 15% super-margin cap), bounded by the hard concentration cap so a black-swan wrong-station resolution can't exceed it. See settings entry below + memory `project_conviction_lock_sizing_2026-06-11`.

**Near-lock conviction sizing (probability path, default-off).** `size_position` takes an optional `prob_cap` (default `None` → `settings.KELLY_PROB_CAP=0.90`). `KELLY_PROB_CAP` clamps `model_prob` before Kelly, so a bet bought **above 0.90 is sized to $0 with reason "no edge"** (`effective_prob/price − 1 ≤ 0`) — which structurally forbids the near-lock band (prices 0.90–0.97) that `PROBABILITY_MIN_ENTRY_PRICE=0.80` is meant to harvest. The probability-path call site in `job_unified_pipeline` passes `prob_cap=NEAR_LOCK_CONVICTION_PROB_CAP` (0.99) when `near_lock_conviction_eligible` (in `binary_market.py`) is True. **Gate rebuilt 2026-06-21** — it now requires a GENUINE observational monotonic lock, not a prob/hours proxy: `has_forecast=True` (excludes degenerate Open-Meteo-failure states) AND the **target-day-anchored** observed max (`_market_daily_max(state, end_date, now_utc)`, NOT `state.current_max_f` — avoids the cross-day leak) already clears the threshold by `NEAR_LOCK_CONVICTION_MARGIN_F` (2.0°F, hedges resolver divergence) in the **betting-hot direction only** (`BUY_YES` on `at_least`/`above` or `BUY_NO` on `at_most`/`below`). Threshold ops only; bracket-like excluded. The full cap cascade (per-trade `MAX_POSITION_PCT`, exposure, USD, depth) + drawdown multiplier still bound the stake. **Why the rebuild:** the original gate (`prob ≥ 0.99 AND hours_until_peak ≤ 0`) fired 96% on degenerate forecast-failed states (Open-Meteo down → `htp=0`, `σ=NULL`, `peak==current_max`), amplifying exactly the NO/forecast bets the HARD-lock path correctly refuses (it requires `has_forecast`); a Seoul NO was sized $13 on a broken 23°C forecast. Master switch `NEAR_LOCK_CONVICTION_SIZING_ENABLED` (default False). `decision_logs.metadata.conviction` flags eligible decisions. See memory `project_conviction_degenerate_state_bug_2026-06-21`.

**Near-peak floor-up.** Both sizers take an optional `floor_to_usd`: when the post-cap stake lands in `(0, MIN_TRADE_USD)`, the stake is floored up to `min(floor_to_usd, tightest_cap_ceiling)` via `_apply_floor` *instead of* dropping to 0 — but only if that result is still ≥ `MIN_TRADE_USD` (so the floor can never breach a cap). Reason becomes `floored to $X (near-peak)`. The floor is **pre-drawdown-multiplier** — CAUTION/RECOVERY 0.5× still applies on top (set the floor to 2× MIN to survive half-sizing), and a PAUSED multiplier of 0 still zeroes it. Callers gate via `near_peak_floor_eligible` (in `binary_market.py`): **threshold ops only** (`exactly`/`range`/`bracket` excluded — validate-first) AND (recorded prob ≥ `NEAR_PEAK_FLOOR_UP_MIN_PROB` OR `|hours_until_peak| ≤ NEAR_PEAK_FLOOR_UP_MAX_HOURS`). Master switch `NEAR_PEAK_FLOOR_UP_ENABLED` (default False). Motivation: at small bankroll, Kelly (× `KELLY_PROB_CAP`) sizes high-confidence near-peak threshold bets below $5 and drops them — the dominant volume throttle once drawdown is healthy. Success-path `decision_logs` carry `metadata.floored_up` for attribution.

#### Drawdown state machine (`src/risk/drawdown.py`)

Four states. Multipliers in parentheses:

| State | When | Multiplier |
|---|---|---|
| `NORMAL` (1.0) | `current_bankroll ≥ peak`, OR `dd_pct < CAUTION_THRESHOLD (10%)` while previously NORMAL |
| `CAUTION` (0.5) | `dd_pct ≤ PAUSE_THRESHOLD (20%)` |
| `PAUSED` (0.0) | `dd_pct > PAUSE_THRESHOLD` |
| `RECOVERY` (0.5) | `dd_pct < CAUTION_THRESHOLD` AND previous was CAUTION/PAUSED/RECOVERY — hysteresis so the bot doesn't snap back to full size on a single up-tick |

Exit `RECOVERY` → `NORMAL` only when `current_bankroll >= peak`.

The `CAUTION_THRESHOLD` / `PAUSE_THRESHOLD` are **Settings-overridable** (`DRAWDOWN_CAUTION_THRESHOLD=0.10` / `DRAWDOWN_PAUSE_THRESHOLD=0.20`; `check()` reads them live, module constants are the defaults) — widen for a small iteration-mode bankroll that a stale peak would otherwise perma-PAUSE. **Peak is reloaded on a TTL:** `_get_drawdown_monitor()` re-calls `load_state()` every `_DRAWDOWN_PEAK_RELOAD_TTL=300s`, so `admin reset-drawdown-peak` (a newer `bankroll_log` row with `peak=equity`) takes effect on the running process within ~5 min **without a restart**. Reloading a *lower* peak is safe: `check()` re-maxes against live equity, so it can only relax an over-tight pause, never under-protect.

#### Bankroll = equity, not wallet liquidity (`src/resolution.py`)

`get_current_bankroll(session)` returns **equity**:

```
bankroll = wallet_usdc
         + Σ (stake_usd / entry_price × per_share_value) for OPEN trades
         + Σ (stake_usd + pnl) for trades WHERE status=WON AND redeemed_at IS NULL
```

where `per_share_value` is `Market.current_yes_price` for `BUY_YES`, `1 - current_yes_price` for `BUY_NO`, falling back to cost basis when missing. Both unsettled lifecycle stages (OPEN on-book and WON-unredeemed) must be included; otherwise the drawdown monitor trips PAUSED whenever the bot has unresolved trades.

Wins don't auto-settle — run `bet redeem --all` to convert WON conditional tokens to USDC. The default path is **DB-driven**: it queries `Trade(status=WON AND redeemed_at IS NULL)` directly, groups by `(market_id, direction)`, and reads the redemption metadata (`condition_id`, `neg_risk`, `clob_token_ids`) from the local `markets` row for that bounded set — scaling with WON-unredeemed count, not lifetime trade count. These three columns are populated on every `job_scan_markets` tick from the Gamma payload (see `_market_to_row` in `src/ingestion/polymarket.py`), so any market scanned at least once while live has metadata cached before it resolves. For legacy rows where the columns are NULL (market resolved before this caching existed), redeem falls back to a single bulk `data-api.polymarket.com/positions?user=<funder>` call: every on-chain position the wallet holds — including resolved-but-unredeemed — comes back keyed by `asset` (= `trades.token_id`) with `conditionId` + `negativeRisk`. CLOB `/markets/<conditionId>` is then called once per missing condition to fill the sibling token_id for `clob_token_ids` (skipped when the user owns both YES and NO — both `asset`s are already in the data-api response). Recovered metadata is persisted back to `markets`. If data-api returns no position for the token, the market is logged and skipped (operator runs `--full-scan` as the last-resort recovery). A Gamma `?clob_token_ids=` fallback was removed — Gamma drops resolved markets from its indexes and silently ignores the camelCase form, so it's unsafe to treat as authoritative. `resolve_trades` setting `status=WON` at resolution time IS the "redeemable" mark; no separate flag exists. `--full-scan` falls back to the legacy flow that paginates the entire CLOB trade history via `get_trades_history` + `compute_positions` — slower, kept as a safety net when local DB may have drifted from on-chain state. Either path stamps `Trade.redeemed_at = now()` on every WON row whose `market_id` matches a successful `redeemPositions()` receipt (`Market.id` is the **Gamma integer id**, not the on-chain condition_id — the condition_id is read from Gamma's `conditionId` field at redeem time and passed to `redeemPositions()`). At the end of every run (and as the sole action when invoked with `--reconcile`), an idempotent reconciliation pass queries on-chain `balanceOf` for every WON-unredeemed Trade and stamps any whose tokens are already gone — this self-heals positions redeemed via the Polymarket UI, redeemed before stamping existed, or that have fallen out of the CLOB trade-history window. Trades whose `token_id` is NULL get resolved via Gamma's `clobTokenIds` (cached per-market) and persisted back. `BankrollLog` is written at 22:00 UTC by `job_daily_settlement`. `get_unredeemed_won_payout(session)` and `get_open_trade_value(session)` expose each adjustment for diagnostics.

`bet portfolio` follows the same DB-first pattern as `bet redeem`: by default it queries `Trade(status=OPEN OR (status=WON AND redeemed_at IS NULL))`, eager-loads `Market` via `selectinload`, and fetches live best-bid/ask for every position in parallel via `asyncio.gather(asyncio.to_thread(get_best_bid_ask, …))` — replacing the prior per-position sequential `get_last_trade_price` round-trips. `--all` extends the set to WON-redeemed + LOST (rendered with realised PnL = payout − cost). `--full-scan` falls back to the legacy walk that pulls the entire CLOB trade history via `get_trades_history` + `compute_positions` and then probes on-chain `balanceOf` to filter redeemed-but-resolved tokens; use it as a safety net when positions may have been taken outside the bot. Helpers: `_load_active_positions_from_db()` (DB path) and `_load_active_positions()` (legacy CLOB path) — both return the same `(ordered, token_to_market)` shape; `bet sell` still uses the CLOB-walk helper.

### Circuit breakers (`src/risk/circuit_breakers.py`)

Checked once per unified pipeline tick *and* every fast-poll tick, before any city is evaluated:
- Daily loss stop: halt when today's P&L < `-DAILY_LOSS_STOP_USD` (-$200).
- Consecutive loss stop: `CONSECUTIVE_LOSS_PAUSE_COUNT` LOST trades in a row (3) → pause `CONSECUTIVE_LOSS_PAUSE_HOURS` (2h). `_paused_until` lives in process memory; consecutive losses are re-queried from DB each check.
- **Submission-failure stop**: `SUBMIT_FAIL_PAUSE_COUNT` (5) `exception:*` orders in the last `SUBMIT_FAIL_PAUSE_WINDOW_MINUTES` (10m) → pause `SUBMIT_FAIL_PAUSE_MINUTES` (30m) and 🚨 Telegram-alert. Counts rows with `trades.exchange_status LIKE 'exception:%'`. Catches a Polymarket protocol migration / wallet-allowance break before it buries the decision logs.

Per-city routine-count and bias-runaway checks live in the aggregator and edge filter, not here.

Falls back to time-to-close when `hours_until_peak` is unknown. Bracket-like was the worst trade class far from peak (loss-making in the 12-24h band, +EV in 0-12h). Per-trade EV is U-shaped in the **effective price of the side bought**: +EV at the extremes (deep-value `[.40,.60)`, near-lock `[.85,1.0]`) and −EV in the mid "overconfidence valley" `[VALLEY_PRICE_LOW, VALLEY_PRICE_HIGH)` where the bot's realised avg NO price (~0.75) sits (60d go-forward: valley −0.054 EV/$1). Two layers in `binary_market_edge`, applied to the chosen side after every other guard under the `reason is None` guard (so a more specific reject reason wins), **probability path only** (the lock path doesn't route through `binary_market_edge`), operator- and side-agnostic: **P1** (`VALLEY_BLOCK_ENABLED`) blocks any side-price in the valley — robust, no tuned param, the interim guard (in-sample 60d EV/$1 0.033→0.093, win 75→81%, volume −40%); **P2** (`VALLEY_MIN_EDGE`) instead requires a raised edge floor in the valley (higher PnL — keeps the +EV high-edge valley trades — but the 0.15 threshold is in-sample-tuned on n=8, validate first). Signals live in `src/signals/probability_engine.py` as `_apply_*` helpers. Each takes `(center_or_sigma, state, reasoning)`, returns the updated value, and appends a one-line explanation to `reasoning`. The monotonicity constraint is applied last.

## Testing Conventions

Tests in `tests/test_<module>.py`. Mock external APIs at the module boundary (e.g. `@patch("src.signals.state_aggregator.fetch_forecast")`). `AsyncMock` for async functions; session mocking via `AsyncMock()` with explicit `session.flush = AsyncMock()`. Do **not** run `ruff` — not used on this project.

## Live Execution

Orders placed via `py-clob-client` in `src/execution/polymarket_client.py::place_order`.

**Flow per trade:**
1. Scheduler creates `Signal` + `Trade(status=PENDING)`.
2. `place_order` checks `DAILY_SPEND_CAP_USD`, resolves YES/NO token IDs (Gamma), places FOK market order.
3. On fill: trade → `OPEN`, `order_id`/`fill_price`/`filled_size` populated, Telegram alert.
4. On failure: trade stays `PENDING` (no retry logic), warning logged.

**Safety:**
- `AUTO_EXECUTE=false` (default) — no orders sent; signals still logged + Telegram-notified.
- `POLYMARKET_PRIVATE_KEY` empty → dry-run; `py_clob_client` never imported.
- `DAILY_SPEND_CAP_USD` — hard 24h rolling cap (default 200; live `.env` overrides to 400).
- `MIN_STAKE_USD=5` — orders below this skipped after drawdown multiplier.
- `DrawdownMonitor` multiplies stake by level (`NORMAL=1.0`, `CAUTION=0.5`, `PAUSED=0.0`, `RECOVERY=0.5`).

## Telemetry (calibration data sources)

Migration `j0k1l2m3n4o5_strategy_telemetry`. `signals` carries one row per `(market_id, direction)` — the chosen-trade rationale; the streams below capture surrounding evaluation context.

- **`evaluation_logs`** — append-only row per per-side edge evaluation. Written by `_log_evaluation` from BOTH paths (after `_binary_market_edge`, after `evaluate_lock` + at rejection points). Captures `model_prob/market_prob/edge/passes/reject_reason/depth_usd/minutes_to_close/routine_count/signal_kind`, plus **forecast/observation context `forecast_peak_f/current_max_f/hours_until_peak/forecast_sigma_f`** (added 2026-05-23, migration `p6q7r8s9t0u1`) so the single-bucket NO guards can be recomputed and their margins re-fit from telemetry alone — `minutes_to_close` measures lead to *close*, but the peak-relative lead gate and the landing-band guard need `hours_until_peak` + `forecast_peak_f` + `current_max_f`. `forecast_sigma_f` is the ensemble peak σ (tracks the σ-collapse root cause). NULL on lock-path rows without forecast context and on pre-migration rows. Use this — not `signals` — for filter-tuning backtests, since `signals` only carries passing edges and is deduplicated.
- **`decision_logs`** — append-only row per per-side **post-filter** decision (added 2026-05-16). Closes the funnel between `evaluation_logs.passes=true` and `Trade` row written: outcomes cover both success branches (`trade_pending`/`trade_filled`) and skip/failure branches (`dup_blocked_*`, `stake_below_min`, `drawdown_paused`, `cluster_cap_hit`, `no_fill`, `order_failed`). Wired into 12 call sites across `src/scheduler/__init__.py::job_unified_pipeline` (probability path) and `src/execution/lock_rule_executor.py::try_lock_rule_trade` (lock path). Use this when investigating "evals passed but no Signal/Trade rows" — the failure mode that cost ~4h of debugging on 2026-05-16. The `stake_below_min` / `drawdown_paused` metadata also carries `size_reason` (which cap binds — per-trade, exposure, USD, depth, MIN_TRADE_USD floor — taken from `PositionSize.reason`), `kelly_pct` (raw fractional Kelly), and `depth_usd` (orderbook depth at decision time) so subsequent debug can identify the binding constraint in one query (added 2026-05-17).
- **`trades.submit_yes_bid` / `submit_yes_ask` / `submit_depth_usd` / `submit_at`** — populated by `place_order` before FAK (live AND dry-run). Lets slippage analyses decompose `fill_price - entry_price` into spread vs depth-walked.
- **`signals.signal_kind`** ('probability' | 'lock') + **`signals.lock_branch`** ('easy_super' / 'easy_standard' / 'hard' / 'bucket_overshoot' / 'range_overshoot' (legacy) / 'range_undershoot' / 'range_in_window') + `lock_routine_count` + `lock_observed_max_f` — set by `_upsert_signal` on every refresh.

## Gotchas

- **Data day = `end_date`'s UTC date = the question-text day (`resolve_target_local_day`).** Polymarket daily-temp markets close at `end_date` = the title day at **noon UTC**, and that UTC date IS the station-local data day for BOTH hemispheres. Both `should_skip_future_day` and `_market_daily_max` (lock path) anchor on it. **Consequence:** a −UTC city's noon-UTC "today" market expires by local morning (before its peak) and the next-day market is correctly skipped, so **Americas trade volume is lower** — by design (those markets weren't profitable; the prior day-early behavior was unsound). The legacy UTC-date fallback in `should_skip_future_day` (no `station_icao`) is unchanged. See memory `project_data_day_fix_2026-05-26`.
- **Near-resolved skip is 0.99 / 0.01**, not 0.95 — so the lock-rule path can evaluate prices in the 0.90–0.99 zone (Wunderground UI catches up later than the METAR feed).
- **Lock-rule fires before the near-resolved skip.** Phase 2 runs `_try_lock_rule_trade` first; only if it returns `None` does the probability path see the market. A fires-but-rejects (price/depth/close-buffer) returns `0.0` and the market is skipped for the rest of this tick.
- **HARD / range-undershoot requires `hours_until_peak <= 0` pre-peak guard.** Without it, overnight radiative cooling makes the 6h trend regression negative and the past-peak OR check fires NO locks hours before daytime heating begins.
- **Dedup is DB-backed first, in-process second.** `_has_active_trade(session, market_id, direction)` is the durable safety net used in BOTH paths: any PENDING/OPEN Trade row short-circuits a second attempt. In-process `_unified_fired_today` / `_locked_markets_fired_today` are same-tick speed-ups. `uq_signals_market_direction` + `_upsert_signal` (single atomic ``INSERT ... ON CONFLICT DO UPDATE ... RETURNING``) prevents duplicate Signal rows on repeat ticks — race-safe at the DB level, no longer relies on APScheduler `max_instances=1` to serialize a SELECT/INSERT window.
- **Fast-poll lock-rule dedup is aggressive on filter rejects** — `_locked_markets_fired_today.add(market.id)` fires even when filtered out (depth, close buffer). Cleared per-station at local-day rollover.
- **Per-station rollover, not global UTC clear.** `_maybe_clear_per_station_caches` runs every unified tick. The dedup→ICAO link is `_market_to_icao` at lock-fire time; entries added outside `job_fast_lock_poll` won't be found by rollover.
- **Fast-poll projection check needs a warm `_state_cache` (30-min TTL).** No-op for a station until `aggregate_state` has run for it once. After a restart, the first ~5 min of fast-poll alerts are silent. `_state_cache` is in-process and never persisted.
- **`job_resolve_trades` ≠ `job_daily_settlement`.** Resolution is a 5-min job; settlement (22:00 UTC) only does bankroll/drawdown bookkeeping, daily summary, redeem nudge, station bias, and weekly calibration.
- **Resolution is chain-gated, not CLOB-gated.** `resolve_trades` calls `bet_helpers.get_payout_outcome(condition_id)` → `payoutDenominator` on the Polygon ConditionalTokens contract as the **primary** signal. If UMA has reported (denom > 0) → map `payoutNumerators` to YES/NO and settle. If UMA hasn't reported and we're past `RESOLVE_NO_PRICE_GRACE_HOURS` (4h): null-fill rows → mark LOST (release exposure, order never landed); populated-fill rows → log WARNING telling the operator to run `admin reconcile-stuck`. The legacy CLOB-mid 0.95/0.05 heuristic (`_refresh_market_price`) is fallback only — used when `market.condition_id IS NULL` or the Polygon RPC fails. (The pre-fix CLOB-mid gating flipped trades to WON before on-chain UMA reporting, producing false `💸 redeem` nudges — see memory `project_chain_gated_resolution_2026-05-19`.)
- **`job_reconcile_orders` includes WON+null-fill.** Status filter is `PENDING/OPEN/WON` (LOST stays excluded — null-fill there is permanent). Backfills fill data on terminal rows that `resolve_trades` flipped before fill details landed; recomputes `pnl` against the corrected `entry_price` when the trade is already WON.
- **Postgres `tradestatus` enum stores uppercase names** (`'WON'`/`'LOST'`/`'OPEN'`/`'PENDING'`). Raw SQL must use the uppercase form (SQLAlchemy uses enum names, not `.value`).
- **`projected_max_f` in `forecast_exceedance_alerts` is the single `_project_daily_max` (halflife) value** (the v2 residual-slope projector + `legacy_projected=` A/B logging were removed 2026-06-24).
- **Dry-run trades stay `PENDING` in BOTH paths and keep their requested `stake_usd`.** `place_order`'s dry-run branch sets `trade.exchange_status="dry_run"` without touching `stake_usd`. Both executors check that flag, leave `status=PENDING`, and emit a "(dry-run)" Telegram alert. **Invariant for new code:** any future query summing `Trade.stake_usd` must filter on `status IN (OPEN, WON, LOST)` (or exclude `exchange_status='dry_run'`); otherwise dry-run rows double-count.
- **Hong Kong (VHHH), Tel Aviv (LLBG), and Taipei (RCTP) are silently skipped** even though they're in `CITIES`/`CITY_ICAO`. `_EXCLUDED_ICAOS` filters them at grouping because their Polymarket resolution station diverges from the routine METAR feed. RCTP (Taoyuan, coastal) added 2026-06-21: reads systematically COOL vs the downtown-Taipei resolver (`market_resolutions` mean −1.85°F / worst −3.6°F; a HARD-lock NO on "≥38°C" lost when RCTP read 35°C but the resolver hit ≥38°C).
- **Bracket markets (`parsed_operator IN ('bracket','range')`) are silently skipped by default** — `BRACKET_MARKETS_ENABLED=False` gates BOTH unified pipeline AND `job_fast_lock_poll`. Threshold/`exactly` unaffected by *that* gate (but see the next two bullets).
- **`exactly` markets are lead-gated in the probability path.** `binary_market_edge` rejects bracket-like edges (`exactly`/`range`/`bracket`) evaluated more than `EXACTLY_MAX_LEAD_HOURS` (12) before the forecast **peak** (`hours_until_peak`, falling back to time-to-close when unknown) — they were the bot's worst trade class far from peak. The gate fires *after* `_check_filters` under a `reason is None` guard, so an already-failed edge keeps its original reason; the `bracket-like lead …` reason only marks edges that would otherwise have passed. Threshold ops are exempt.
- **`place_order` does a wallet pre-flight before submitting.** Right after the daily-spend-cap check, it calls `get_wallet_usdc_balance(force_refresh=True)`; if live CLOB-visible spendable < `trade.stake_usd`, it short-circuits with `trade.exchange_status="insufficient_balance"` and `return False`. Callers route this to the `OUTCOME_INSUFFICIENT_BALANCE` `decision_log` outcome (else `OUTCOME_ORDER_FAILED`) — separates intentional hold-back from "tried and lost". Catches the burst-placement balance race (local exposure cap lags on-chain reality) that produced `exception:PolyApiException` rows. No-op for dry-run and for `get_wallet_usdc_balance()→None`. Memory: `project_polyapi_balance_race_2026-05-30`.
- **Bracket-like NO is killed in the live `.env`** (`BRACKET_LIKE_NO_DISABLED=True`) and **single-bucket NO has three layered guards** in `binary_market_edge`. Root cause: each single-°C bucket is evaluated as an **independent** binary, so a tight Gaussian on an over-forecast peak makes every neighbouring bucket look near-impossible → incoherent "NO on every adjacent bucket". Guards (NO-side only, `op in (exactly,range,bracket)` only, no-op when forecast context `None`): (1) peak-relative lead gate (`EXACTLY_MAX_LEAD_HOURS`); (2) landing-band (`SINGLE_BUCKET_NO_BAND_MARGIN_F`); (3) overconfidence cap (`SINGLE_BUCKET_MAX_NO_PROB`). `forecast_peak_f`/`current_max_f`/`hours_until_peak` are threaded in from the `job_unified_pipeline` call site. See the Settings entries above for values + the deferred σ-recalibration that gates re-enabling.
- **`market_snapshots.yes_price` (Gamma) is STALE in the repricing window — never price a backtest with it.** Inside the 45 min after a market-moving METAR it correlates only **0.31** with the real CLOB book and runs **+0.142 too high** (34% of points off by >0.10), because Gamma keeps quoting the pre-move price for ~10 min. The bot's own `shadow_ledger` bid/ask (from `get_best_bid_ask`) tracks the book at **corr 0.974**. Pooled over a market's whole life the two agree (corr 0.99) — **that pooled check is a trap.** The bias is directional (the dying YES bucket still looks expensive ⇒ NO looks cheap), so a snapshot-priced backtest of any post-METAR NO rule invents a huge fake edge. Price execution studies from `clob.polymarket.com/prices-history` (1-min fidelity) or live `get_best_bid_ask`. Also note `shadow_ledger` is **censored** (the pipeline skips `yes_bid≥0.99 or yes_ask≤0.01`), so post-collapse rows are absent and a naive `merge_asof` silently matches a pre-collapse quote. See memory `project_gamma_snapshot_stale_2026-07-10`.
- **`fetch_latest_metars` returns only each station's MOST RECENT METAR.** `job_fast_lock_poll` built its `WeatherState` from that alone → a 1-point `routine_history` → `evaluate_lock`'s `routine_count < 2` hard floor → **every fast-poll lock was a silent no-op** (which also explains the conviction-lock path's zero fires). Fixed 2026-07-10 by merging the day's routine history from `state_aggregator`'s `_state_cache` (30-min TTL, in-process, no extra HTTP) before building the state. Any future fast-poll state builder must do the same.
- **The `range_overshoot` NO lock was removed 2026-06-24 and that removal was WRONG** — restored 2026-07-10 as `bucket_overshoot`. Its "56%/−$57.61" was phantom-inflated (real book: 9 fills, 89% win, −$3.70) and its single real loss was the pre-2026-05-26 wrong-day bug on a −UTC city, not °C resolver divergence. **Lesson: before killing a branch, filter `fill_price NOT NULL` and check whether its losses predate a known input bug — a rule can be correct while its inputs are wrong.** See `docs/graveyard.md`. **`range_undershoot` NO lock is gated by `RANGE_UNDERSHOOT_LOCK_ENABLED` (code default `True`, live `.env`=`False`) since 2026-06-03** — the win%-vs-price audit showed it is ~9pp **model-overconfident** (won 71.4% vs an 80.8% price-implied break-even, −$26.52/30d), the same win-small/lose-big shape as the killed bracket-like NO; this is a σ-collapse symptom (σ too tight on narrow windows), **not** a resolver divergence (measurable divergence is unbiased ±0.1°F), so the cure is the lead-time-aware σ floor, not a °C correction. Because the code default is `True`, the gate engages **only when the `.env` line is set** — a fresh deploy without it leaves the branch firing. `range_in_window` (YES) still fires under both flags. See the lock-rule Settings entry; re-enable only after the σ floor lands and the class turns +EV. **Phase-3 audit (2026-05-31, `scripts/backfill_market_resolutions.py --commit` → `resolution-report --days 120`, 535 settled rows, 0 pending):** the audit did **NOT** confirm a systematic hot bias — °C-city mean divergence ≈ **−0.00°C (n=465)**, largest per-station means only ±0.3°C on thin n (KJFK −1.0°F/n7, RCTP −0.31/n16, RKPK +0.28/n13), only **175/535 rows are *measurable*** (have ≥1 finite implied bound); the other **360 (67%) are structurally blind** — bracket/threshold **NO** outcomes imply `(None,None)` so `divergence_f` is forced to 0.0 (a known property of `implied_max_bounds`, not a bug; the report's 0.00 rows are mostly these). On the 175 measurable rows: **mean −0.05°F, abs-mean 0.28°F**; only 26 are nonzero and **all are `yes_won=True`** (a YES bracket/`exactly` is the only outcome that pins a tight interval), spread *both* signs (−7°F KJFK … +3.6°F ZGSZ/RKPK). So at current volume the long-standing "we read hotter than the resolver" theory is **unsupported** — do NOT build a divergence correction yet. Limitation to keep in mind: the divergence metric only sees YES-pinned outcomes, so it can't measure the NO-side bleed directly; widening coverage needs settled all-bucket events to back-solve a point resolved-max. Next: accrue more data (re-run the idempotent backfill + report), manually verify resolver stations for the few nonzero outliers before acting.
- **Cluster-cap helper anti-correlation guard.** `_cluster_stake_used` sums currently-staked $ across same `parsed_location` + same `end_date.date()` (UTC) bracket/exactly cluster, excluding dry-run rows. Both paths reject if `cluster_used + new_stake > settings.CLUSTER_STAKE_CAP_USD`. Threshold markets unaffected (helper returns 0.0 for non-bracket-like operators).
- **`apply_calibration` is on by default but degrades gracefully.** Needs ≥`MIN_CALIBRATION_SAMPLES=50` resolved trades. Below that, `get_calibration_coefficients` returns None and `apply_calibration` returns the raw probability unchanged with `applied=False`. Cache TTL 30 min in `_CACHE_TTL_SEC`.
- **`MIN_EDGE` is harmonised on `settings.MIN_EDGE` (default 0.05).** `_check_filters` reads `settings.MIN_EDGE` directly (the former module-level `edge_calculator.MIN_EDGE` re-export was removed). **Live prod (DO app spec, `doctl apps spec get` — authoritative) sets `MIN_EDGE=0.05`** (= the default; an earlier `.env` used `0.10`). Verify via doctl before assuming; the DO spec, not `.env`/`.do/app.yaml`, is ground truth (confirmed 2026-07-09).
- **`_fetch_orderbook` caches only successful fetches (30s).** Failures are not negative-cached, so two back-to-back calls to a dead token retry 3×3×throttle delay — except 404 ("No orderbook exists for the requested token id"), which short-circuits to `None` on attempt 1 and is silenced by `_CloudflareNoiseFilter`. Resolved markets surface as 404 here.
- **Orderbook depth must be probed at the per-side BUY price (the ask), NOT the mid** (fixed 2026-06-14). `_compute_depth(book, price)` sums asks with `ask_price <= price`; on any positive spread the best ask sits above the mid, so probing at the mid returns **0 every time**. `job_unified_pipeline` previously probed YES depth at `live_price` (the mid) → `mkt_depth=0` always → the `depth >= MIN_DEPTH_USD` filter silently vetoed **every BUY_YES on both the probability path AND the EASY-YES lock path** (so the conviction-lock sizing was inert), while the NO side already probed at its true ask (`1 − yes_bid`) — a mechanical co-cause of the all-NO book previously attributed solely to σ-collapse. Now probes at `yes_ask`. **`job_fast_lock_poll` had the same bug and was fixed 2026-06-18** (it probed YES depth at `yes_price=(yes_bid+yes_ask)/2` → understated depth vetoed near-certain EASY-YES locks, the conviction-lock target; now probes at `yes_ask`, NO-side re-probes its own ask inside `try_lock_rule_trade`). Regression tests: `tests/test_polymarket_client.py::test_compute_depth_at_mid_is_zero_but_real_at_ask` + `::test_fast_poll_yes_depth_probes_ask_not_mid`. Any new depth probe MUST pass the buy price, not the mid.
- **`_get_client()` is thread-safe via `_client_build_lock`.** `bet portfolio` fans out `get_best_bid_ask` through `asyncio.to_thread`; without the lock every worker raced past the `is None` check and rebuilt the client, each posting to `/auth/api-key`. `bet_helpers.get_clob_client` now delegates to the same singleton instead of building its own. The 400 `Could not create api key` line (transparently retried as a GET-derive by the SDK) is also filtered out.
- **FOK orders fully fill or cancel** — no partial fills; thin books leave trades in `PENDING`.
- **`place_order` posts FAK buys via `MarketOrderArgsV2` + `create_market_order`, not `OrderArgsV2` + `create_order`.** CLOB enforces stricter precision on FAK/FOK buys; the limit-order builder triggers `400 invalid amounts`. We pass our tick-snapped `limit_price` so the SDK skips its network `calculate_market_price` call.
- **`delayed` orders post successfully but aren't yet retrievable.** `post_order` returns `status="delayed"` with a real `orderID`, but `client.get_order(order_id)` returns None until the matching engine picks it up. `_update_fill_details` guards against None so the trade keeps `status=PENDING`, `exchange_status="delayed"`. The fill-details call in `place_order`'s success branch is wrapped in its own try/except so a lookup failure can't orphan a live order. `job_reconcile_orders` re-runs `check_order_status` on a 5-min cadence to populate `fill_price`/`filled_size` once the engine retrieves the order.
- **`WeatherState` is produced even if Open-Meteo fails** — `forecast_peak_f = current_max_f`, `hours_until_peak = 0`, `has_forecast = False`. HARD-direction lock disabled; probability degenerates.
- **`_paused_until` circuit-breaker state survives restart via `bot_state`.** The in-process variable is hydrated from `bot_state.value['until_iso']` on the first `check_circuit_breakers` call after boot; subsequent calls read in-process. Writes (engage / clear-on-expiry) write-through to DB so a crash mid-pause doesn't drop the protective window. Consecutive-loss counting is still re-queried each tick — the persisted pause is the *length of the window*, not the streak count. **Fail-open on missing table:** if the `m3n4o5p6q7r8_bot_state_table` migration hasn't been applied, `_load_paused_until` / `_persist_paused_until` catch `ProgrammingError`, log a warning, and return None rather than killing the pipeline (a missing-table deploy once silently halted every tick — always run `alembic upgrade head`; `create_all` isn't a substitute on managed Postgres).
- **`Market.current_yes_price` is read-only in the unified pipeline, fast-lock poll, and `resolve_trades`** — they take the live mid from `get_best_bid_ask` into a local `live_price` and never assign back to the ORM row (the dirty Market would otherwise autoflush with `session.add(Signal/Trade)` and cause cross-transaction deadlocks). Only `job_scan_markets` (`ingest_markets`) persists this column, iterating sorted by id so UPDATEs are emitted in deterministic primary-key order.
- **Polymarket Gamma `/markets` listing no longer surfaces weather markets** — `?tag=weather`, `?feeType=weather_fees`, `?negRiskMarketID=…`, `?category=Weather` are all silently ignored (Gamma returns the default trending listing), and paginating `?active=true&closed=false` returns 0 weather markets. Don't retry these. `fetch_weather_markets` uses **event-slug enumeration** as the primary path: `/events?slug=highest-temperature-in-<city>-on-<month>-<day>-<year>` (every city in `CITY_ICAO` × next `_EVENT_SLUG_LOOKAHEAD_DAYS` days, concurrent under `Semaphore(8)`). City-name → Polymarket-slug overrides live in `POLYMARKET_CITY_SLUG_OVERRIDES` (e.g. NYC's slug is `nyc`); add a row when a city's first scan returns 0 events. Keyword + tag scans are kept as defensive fallbacks.
- **Stuck-OPEN exposure-cap silencer (recurring failure class — see memories `project_exposure_cap_silencer_2026-05-17`, `project_stuck_alert_2026-05-18`).** Unresolved OPEN trades pin `MAX_EXPOSURE_PCT × bankroll` and silently zero every Kelly stake. Current guards: `resolve_trades` fallback marks null-fill LOST (or warns to run `admin reconcile-stuck`) once past `RESOLVE_NO_PRICE_GRACE_HOURS`; `admin reconcile-stuck` settles via on-chain `balanceOf`/`payoutNumerators` and backfills missing `condition_id`; `MAX_EXPOSURE_USD_FLOOR=$300` keeps small-bankroll trading alive; `job_reconcile_orders` runs a 5-min stuck-OPEN heartbeat (`STUCK_ALERT_*`, cooldown in `bot_state`) and a 7-day long-tail lookback. `check_order_status` None-guards `client.get_order` (returns None for queued AND post-resolution-dropped orders).
- **Phantom-LOST: `LOST + fill_price IS NULL` is accounting cleanup, not a realized loss.** `resolve_trades` gates the LOST decision behind on-chain `balanceOf(token_id, funder_address)` (`_query_token_balance`): `bal>0` → `_backfill_null_fill` + preserve OPEN; `bal==0` → LOST with `pnl=0` (release exposure, no invented loss); `bal=None` (RPC unreachable) → conservative `pnl=-stake`. Recovery for legacy phantom rows: `admin reconcile-stuck --include-lost` reverts them to OPEN. Bankroll math must treat such rows as cleanup. See memory `project_phantom_losses_2026-05-20`.
- **Submission-failure circuit breaker** (see Circuit breakers section). Counts `trades.exchange_status LIKE 'exception:%'`; persists the pause via `_paused_until`. Full error body is captured in `Trade.exchange_error` (Text, ≤2000 chars).
